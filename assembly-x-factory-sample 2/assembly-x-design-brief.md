# Assembly X

**Build a rule. Run the factory.**

## Experience at a glance

- **Audience:** All-age beginners working at approximately Grade 6
- **Primary domain:** Expressions and Equations
- **Prototype length:** 8–12 minutes across seven levels
- **Full experience target:** 25–35 minutes with practice and transfer
- **Format:** Self-guided, touch- and keyboard-accessible interactive
- **Primary standards:** CCSS 6.EE.A.2, 6.EE.A.3, and 6.EE.A.4

## Premise

Assembly X is a precise fabrication lab. A sealed crate labeled \(x\) can contain any allowed quantity. The learner cannot open the crate, but can place it on a tray, add individual units, duplicate a complete tray, and reorganize the resulting inventory.

The factory builds exactly what the learner specifies. Its output—not a red “incorrect” message—reveals the mathematical meaning of each instruction.

## Intended conceptual change

Learners often experience expressions as strings of symbols governed by memorized rules. Assembly X reframes an expression as a description of a process and an inventory:

- A variable is a quantity that may take different values.
- Grouping identifies a complete quantity that can be acted on as one object.
- Multiplication duplicates everything in the selected group.
- Distribution is duplication followed by unpacking and reorganizing.
- Equivalent expressions are different plans that produce the same inventory for every allowed input.

## Transfer goal

Given a new expression or production plan, the learner can construct, interpret, test, and revise it—and can justify whether two different-looking expressions are equivalent using structure rather than relying on one matching example.

## Final evidence of understanding

The learner receives Factory A, which builds \(3(x+2)\). They must construct a visibly different Factory B using available modules. A successful plan builds \(3x+6\), passes multiple hidden input tests, and is justified by explaining that both plans always produce three sealed \(x\)-crates and six individual units.

## Prototype progression

| Level | Learner challenge | Intended insight | Primary evidence |
| --- | --- | --- | --- |
| 1. Calibration | Turn 4 into 14 using `+3` and `×2` once each | Order changes a process | Builds `+3 → ×2` and interprets the execution trace |
| 2. Same tools, new order | Turn 4 into 11 | The same operations can produce a different result | Reorders the same modules intentionally |
| 3. Sealed cargo | Add 3 to \(x\), then duplicate the entire tray | Grouping determines the scope of multiplication | Builds \(2(x+3)\) from a variable input |
| 4. Spot the scope | Choose the plan that duplicates the added units | \(2(x+3)\) and \(2x+3\) describe different actions | Connects symbolic grouping to visible behavior |
| 5. Twin factories | Decide whether \(2(x+3)\) and \(2x+6\) always agree | Distribution preserves inventory | Justifies equivalence structurally |
| 6. Counterexample lab | Test \(2(x+3)\) and \(3x+2\) | One matching input does not establish equivalence | Selects an input that makes the outputs differ |
| 7. Certification | Build a plan equivalent to \(3(x+2)\) | Equivalent forms can encode different processes with the same general result | Builds \(3x+6\), passes hidden tests, and explains why |

## Misconception and feedback map

| Learner action or belief | Likely reasoning | Behavioral feedback |
| --- | --- | --- |
| Builds `×2 → +3` for \(2(x+3)\) | Treats the operations as an unordered list | The factory duplicates the \(x\)-crate before the three units arrive, leaving the units outside the duplicated trays |
| Claims \(2(x+3)=2x+3\) | Multiplies only the variable | The execution view places the three units outside the duplicator’s scope |
| Claims two expressions are equivalent after one matching result | Treats evidence from one case as proof | A deliberately chosen input reveals different outputs |
| Rejects \(2(x+3)=2x+6\) because the expressions look different | Uses visual similarity as the test for equivalence | Both factories unpack into the same number of \(x\)-crates and units |
| Can produce the answer but cannot justify it | Procedural success without structural understanding | The final explanation asks the learner to compare inventories, not repeat a rule name |

## Feedback principles

- Never make the factory deceptive; it executes the visible plan consistently.
- Describe what happened before suggesting what to change.
- Ask one diagnostic question at a time.
- Preserve the learner’s work while they revise.
- Treat a failed test as useful evidence, not a penalty.
- Name the distributive property only after the learner has experienced the invariant inventory.

## Visual and interaction direction

- Quiet, futuristic fabrication lab rather than a cartoon factory
- Sealed \(x\)-crates, individual unit pieces, grouping trays, and duplication gates
- One strong signal color; restrained neutral surfaces
- Short, deadpan system messages such as “Built exactly as ordered”
- Satisfying motion that shows scope, grouping, and duplication
- No points, avatars, decorative dashboards, or unrelated game rewards
- Tap/click controls as the accessible baseline; dragging can be an enhancement
- Reduced-motion mode shows discrete execution states without transition

## Mathematical and product validation

Each level should be checked for:

- Mathematical correctness across the full allowed input domain
- Whether alternate valid solutions should be accepted
- Whether the intended solution is possible with the provided modules
- Whether any interaction can create an undefined or misleading state
- Whether feedback correctly distinguishes operation-order and grouping errors
- Visual clarity at phone and desktop widths
- Keyboard operation, readable focus order, and non-color-dependent meaning

## Initial playtest questions

1. Before formal notation appears, what does the learner think a tray means?
2. Can the learner predict what the duplicator will copy?
3. After Level 3, can the learner explain the difference between \(2(x+3)\) and \(2x+3\) without using a memorized rule?
4. Does the matching case in Level 6 create productive uncertainty or confusion?
5. In the final level, does the learner justify equivalence using inventory or only test values?
6. Which actions feel satisfying, slow, unclear, or unnecessary?

## Portfolio framing

Assembly X is an independent prototype created to demonstrate an approach to visual, puzzle-driven mathematics learning design. The final case study should distinguish design intentions from claims supported by playtesting and document the revisions made after observing learners.
